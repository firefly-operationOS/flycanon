# Firefly Intelligence System

> The combined narrative for **flycanon** (operational knowledge repository) and **flyradar** (operations discovery / diagnostic intelligence). These two services were unified across 12 plans on 2026-05-22 to share a ubiquitous language, agent surface, and tenant-isolation model.

## What these services do

### flyradar — process mining + diagnostic intelligence

flyradar turns heterogeneous corpus (logs, system signals, documents, observations) into:

- An AS-IS process graph (BPMN-shaped).
- A dependency DAG across systems.
- Findings: bottlenecks, exceptions, deviations.

It is **stateless about long-lived knowledge**. Each discovery is a job; results are emitted and (optionally) handed off to flycanon for retention.

### flycanon — operational knowledge repository

flycanon is the **long-lived knowledge boundary**:

- Universal ingestion (Sources from any pipeline).
- Hybrid retrieval (pgvector HNSW + Postgres BM25 with Reciprocal Rank Fusion).
- RAG answers with citations.
- Candidate → Accept workflow for human-validated knowledge.
- Per-workspace isolation enforced via Postgres RLS.

flyradar discoveries flow into flycanon via the agent handoff endpoint. flycanon owns the truth across discoveries; flyradar can query it for prior context.

### Shared vocabulary

Every wire contract uses these identifiers in both services:

| Field | Meaning | Where |
|---|---|---|
| `tenant_id` | Customer tenant slug | DTO field + `X-Tenant-Id` header + DB column |
| `workspace_id` | Workspace slug within a tenant | DTO field + `X-Workspace-Id` header + DB column |
| `correlation_id` | Trace identifier | `X-Correlation-Id` header (autogenerated if absent) |
| `actor` | User or agent identity | Audit metadata; `agent:<token-prefix>` for agent calls |
| `agent_token` | Long-lived bearer token | `X-Agent-Token` header on `/api/v1/agent/*` routes |

No `engagement_id`, no `signal_kind` aliases, no service-specific synonyms. See [[feedback-ubiquitous-language]] memory.

### Error envelope (RFC 7807)

Both services emit:

```json
{
  "type": "https://firefly.dev/problems/<code>",
  "title": "...",
  "status": 404,
  "code": "resource_not_found",
  "detail": "...",
  "errors": [{"path": "name", "message": "..."}]
}
```

SDK callers branch on `code` (stable machine-readable), not `title` (human-readable).

## Multitenancy + RLS

Both services enforce **Postgres row-level security** on every table with `(tenant_id, workspace_id)` columns. Migrations:

- flycanon: `0013_rls_policies` covers all 16 `canon_*` tables.
- flyradar: `0006_rls_policies` covers the `flyradar_*` tables.

Application sessions issue `SET LOCAL app.tenant_id = '<slug>'; SET LOCAL app.workspace_id = '<slug>'` per transaction via a SQLAlchemy `after_begin` event listener bound to the ContextVar. The ContextVar is populated by `TenantContextMiddleware` from request headers.

**Deployment requirement:** ops must provision two Postgres roles per service:

- `<service>_admin` — has `BYPASSRLS`. Used by migrations + cross-workspace workers (consolidation, retention, EDA ingest).
- `<service>_app` — no `BYPASSRLS`, NOT a superuser. Used by request-scoped queries.

Without this split, RLS is silently bypassed in production. (FORCE ROW LEVEL SECURITY applies to OWNER, not SUPERUSER.)

## Agent token model

Long-lived bearer tokens minted via `POST /api/v1/agent-tokens` (user-tier, JWT-protected). Format: `agt_<8hex>_<32hex>`. SHA-256 hashed at rest; the 12-char prefix is the public lookup key.

Each token carries:
- `tenant_id` — scope identity.
- `workspace_allowlist` — optional list of workspaces this token can speak for.
- `scopes` — list of allowed scope strings (e.g., `agent.sources:ingest`, `agent.query:run`).
- `expires_at` — optional expiry.
- `rate_limit_rpm` — enforced by `AgentTokenService.verify` via a
  per-token sliding 60s in-process counter; `429 rate_limit_exceeded`
  on budget exhaustion. `None` or `<= 0` disables the check.

Verify path uses `secrets.compare_digest` (constant-time). `mark_used` writes are deduped to a 60s window.

## Cross-service flows

### Flow 1: Workspace lifecycle

```
Operator → POST /api/v1/workspaces (flycanon)
         → flycanon: insert canon_workspaces row, emit WorkspaceCreated on canon.workspaces.v1
flyradar → consume canon.workspaces.v1 → WorkspaceCacheClient populates entry
```

### Flow 2: Discovery → knowledge handoff

```
Operator → POST /api/v1/agent/discovery-jobs (flyradar, agent token + idempotency key)
         → flyradar: enqueue + run discovery
         → on completion, flyradar publishes result internally
Operator → POST /api/v1/agent/canon/handoff (flyradar)
         → flyradar: build SourceSpec from job result
         → flyradar: POST /api/v1/agent/sources (flycanon, agent token + idempotency key)
         → flycanon: ingest source, return source_id
         → flyradar: return source_id to caller
```

### Flow 3: RAG over canon during a discovery

```
flyradar discovery stage → POST /api/v1/agent/query (flycanon, agent token + idempotency key)
                        → flycanon: hybrid retrieval + RAG answer
                        → flyradar: incorporate the answer into discovery context
```

### Flow 4: Candidate → accept

```
flyradar discovery completes → POST /api/v1/agent/candidates:propose (flycanon)
                             → flycanon: store Candidate (NOT auto-accepted)
Reviewer (user-tier) → POST /api/v1/candidates/{id}:accept (flycanon)
                    → flycanon: promote Candidate → KnowledgeItem + KnowledgeVersion
```

## Operational requirements

### Per service

- One Postgres database (with pgvector extension for flycanon).
- Two roles (admin + app) per service.
- An EDA broker for workspace events (in-process default; Kafka/RabbitMQ for production).
- JWT verification keys for user-tier auth.
- Configurable agent token mint policy (e.g., who can call `POST /api/v1/agent-tokens`).

### Cross-service

- flyradar needs a flycanon agent token (set via `FLYRADAR_FLYCANON_AGENT_TOKEN`) for handoff + cache fill.
- Network reachability: flyradar → flycanon HTTPS.
- Time sync: agent token expiry and idempotency TTL depend on it.

## Shared platform capabilities

flyradar and flycanon share a common backbone:

- Shared HTTP conventions: RFC 7807 envelope, tenant-context headers, idempotency primitives, tenant-safe outbound client.
- `(tenant_id, workspace_id)` multitenancy across DB, DTOs, and headers, enforced by Postgres row-level security.
- An agent surface (`/api/v1/agent/*`) protected by hashed agent tokens.
- Cross-service handoff + a cached workspace client.
